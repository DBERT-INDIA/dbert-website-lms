# DBERT course cohorts and study classroom

This offline update connects course cohorts, learner questions, mentor follow-up, milestones, and credentials. The classroom adapts the three-panel layout and Study Trail from [Tutor App](https://github.com/Yasharthpoddar/Tutor-app-) to DBERT’s course, account, and assessment records.

The original source snapshot is `2fdc414`. The earlier platform improvements were recorded in `99efdaa`. This update is in the local `feature/cohort-study-workspace` branch.

## Changes from the original project

| Area | Before | What changed and how it works | Benefit |
| --- | --- | --- | --- |
| Course cohort setup | The original company cohort flow handled company listings, approval, and enrollment. Course learning had separate enrollment and progression. | Admins create a cohort for an available DBERT course, set dates and capacity, assign a mentor, close or reopen registration, and inspect the roster. The first milestone locks the dates used to evaluate activity. | A course has a defined group, a schedule, a staff owner, and stable completion criteria. |
| Course enrollment and capacity | A learner could enroll in a course, and company cohorts had basic seat limits. Course groups lacked a waiting list tied to the learner’s course access. | Eligible learners join from the dashboard. A full group queues members in arrival order. Leaving frees a seat, expansion fills seats, and staff can run a fill after access or account changes. Every promotion rechecks active course access. A database lock serializes seat changes. | Learners keep their place in line and simultaneous joins respect capacity. Course payments and entitlement checks still own course access. |
| Cohort rosters and progress | Staff could see course, mentorship, and company cohort activity on different pages. A learner had no progress view against common requirements. | Admins and assigned mentors have scoped rosters and milestone progress. Learners get a private view of their own counts, targets, due dates, and required milestones. Staff can leave check-ins that the learner can see. | Learners know what to work on and mentors can address a specific gap. |
| Milestone evidence | The LMS tracked quizzes, courses, and projects independently. Staff had to combine that evidence for a program. | Milestones count distinct passed quizzes, approved capstone submissions, distinct lessons discussed in the classroom, or a completed course. When a course requires a capstone, completion also requires approval of the learner’s project. New contributions count from the later of cohort enrollment and the cohort start date. Existing course completion is credited. Due dates show when work is overdue. | Learners see credit for real activity, and repeated questions or quiz attempts cannot inflate distinct counts. |
| Study workspace | The original course classroom had a syllabus and tutor. Learners moved between chat and curriculum without a dedicated place to organize questions or notes. | The version adapted from Tutor App has Study Trail, Tutor Chat, and Lecture panels. Desktop panel widths support pointer and keyboard resizing. On small screens the panels appear as keyboard-accessible tabs. The workspace opens from the learner dashboard, course, and cohort. | Learners stay in context while switching between a question, the reading, and their review plan. |
| Course sources and tutoring | The tutor could discuss lessons, without stable links from a response to the DBERT sections used to answer it. | The server searches the enrolled course’s lesson briefs and key takeaways. An answer carries excerpts from up to three matching sections. Opening a citation selects the lesson and focuses that section. With no matching material, the tutor says so. The default response is a course excerpt. An optional Gemini mode uses the learner’s configured key and sends the current question and selected excerpts. | Learners can check an answer against their course material. The classroom works offline with local data. |
| Durable Study Trail | Questions existed in lesson chat history, with no separate review state. The Tutor App reference used scripted responses and browser state. | DBERT persists questions, answers, citations, and the **Explored** or **Needs review** state for each learner and course. The trail filters flagged questions. Retried questions reuse a request ID, and an older saved entry can be opened through its direct link. | Learners can return later and find the same evidence and review status. A repeated request does not create a second copy of the question. |
| Private lesson notes | The DBERT classroom lacked a dedicated lesson notebook. Tutor App notes were stored in the browser. | Notes are stored for the signed-in learner, course, and lesson. Saves carry a version. If a second tab has saved changes, the stale write is rejected and the current draft can be copied before reloading. | Notes travel with the account and one tab cannot silently overwrite another tab’s work. |
| Review and practice | The platform had concept scheduling and day quizzes. Learners could not send their own questions to a dashboard review queue and practice from them. | **Needs review** joins the dashboard queue. The review shows the original question and linked sources. A graded item uses an existing concept-linked quiz question from a day the learner has passed. A correct answer clears the flag and updates Guided Learning evidence and scheduling. Wrong answers leave the flag active. Where an eligible quiz question is unavailable, learners can complete a reading review. | Learners have a path from confusion to revision. Graded practice and reading reviews have distinct outcomes, and a retried submission is counted once. |
| Mentor study insights | Existing analytics and mentoring did not show common lesson questions for a course cohort. | An assigned mentor or admin sees lesson-level counts from active cohort members during the cohort dates. A lesson appears after at least two learners have asked about it. This view reads aggregate counts and includes no private question, answer, or note content. Staff can assign a lesson follow-up and optional due date to the cohort’s Study Trail. | Mentors can see which lessons merit a group follow-up and can send the group directly to the lesson or available quiz. |
| Cohort completion credentials | The wallet supported existing course and internship credentials. It did not record completion of a defined cohort. | A learner or admin can issue the cohort credential when every required milestone is met. Issuance saves one credential and one evidence snapshot per membership in a transaction. After the first issuance, cohort milestone rules are fixed. The credential appears in the wallet and has a verification and print page. Its separate tier and course linkage preserve ordinary course issuance and formal internship verification. | Learners can demonstrate program completion while course and internship verification retain their existing meaning. |
| Course and account boundaries | Some legacy lesson routes checked the learner’s course enrollment before selecting a lesson by ID alone. | Those routes now also match the lesson to the requested course. New classroom routes check course access and record ownership. New cohort pages check the signed-in role and mentor assignment. The existing CSRF layer protects writes, private responses disable caching, and hard-deleting an account cascades to the new private study records. | Learners cannot open another course’s material or another learner’s private records through the classroom. |

## Demonstration sequence

1. Open **Admin → Course Cohorts**. Create a cohort for a course with lessons and assign a mentor. Set capacity to one and join with two already enrolled test learners to show the waitlist. Raise capacity to two to show promotion.
2. From the staff progress page, add a required **Distinct lessons discussed** milestone. Add a quiz or approved capstone milestone to show how DBERT uses existing course evidence.
3. Open **Study classroom** as a learner. Ask a question whose key term appears in a lesson. Open a citation, add a note, mark the item **Needs review**, and reload to show that all three survive.
4. Open the review from the learner dashboard. Use a completed course day with a concept-linked quiz question to show graded practice. Use another lesson to show a reading review.
5. Ask about the same lesson as the second learner. As the assigned mentor, open **Cohort study insights**, inspect the counts, and post a follow-up. Open the learner’s Study Trail to show it.
6. Complete the required milestones and claim the cohort credential. Open the verification page from the wallet. Return to cohort progress to show the issued credential there as well.

## Fixes found during verification

| Issue found | Fix and benefit |
| --- | --- |
| PostgreSQL startup returned before creating the feature tables. Several Guided Learning writes also requested a generated `id` on tables with named or composite keys. | PostgreSQL and SQLite now use the same feature bootstrap. PostgreSQL holds a migration lock across commits. Quiz receipts and Guided Learning writes return their actual keys. Offline tests exercise the SQLite schema and capture the SQL issued through the PostgreSQL adapter. |
| Account deletion could remove the sole credential receipt that locked a cohort’s milestones. Quiz receipts and listing reports could also block existing account cleanup. | First issuance stores a permanent lock on the cohort. The migration backfills the lock from existing receipts. Account cleanup removes dependent quiz receipts and listing reports in the same transaction. |
| The last quiz counted as course completion for cohort milestones even if a required capstone was pending. | Cohort completion now checks the learner’s approved capstone when required. The last quiz clearly reports what was completed and links to the required project. |
| Quiz navigation could advance twice per click, a reload returned learners to the first question, and the result dialog could stay hidden after grading. | A click advances one question after an answer is selected. The browser restores the active question with saved answers. Submission opens the result dialog and moves focus to the result. |
| Citation excerpts could omit relevant text late in the source. The same-day analytics boundary could count a question asked before cohort enrollment. | Citations preserve the relevant passage. Mentor counts use the enrollment timestamp. Study Trail practice links appear when a review or quiz is available, and lecture follow-ups reopen the Lecture panel on mobile. |
| Search and Verified Fellows lacked central SEO metadata. Failed public certificate deep links could leave visitors without an error or a way to retry. | Both routes have metadata. The verifier restores the submitted ID and announces the error, so visitors can correct and resubmit it. Article and certificate headings follow the page hierarchy. |

## Offline verification

Run from the repository root.

```powershell
python -B scripts/verify_offline.py --browser
```

The expanded run passed **130 Python tests, 4 Node tests, and 8 Chromium tests**, plus the Compose configuration, Flask/Jinja syntax checks, and SEO checks for 82 routes. The study and cohort tests exercise the real Flask blueprints with synthetic SQLite records. Chromium tests use intercepted responses and cover quiz submission and recovery, classroom resizing, mobile tabs, citation navigation, and note conflicts. A separate Chromium check exercised the public certificate verification form’s retry flow. Credential tests cover both issuance orders and formal internship status. One legacy unsubscribe test requires the full Flask runtime and was excluded from the offline suite.

The default classroom requires an authenticated learner with course access and stored lesson text. It displays the most recent 100 questions plus a directly linked older entry. Tutor replies arrive as completed responses using local excerpts by default. A configured portal can enable generation with `STUDY_CLASSROOM_USE_GEMINI=true`.

Full Flask startup remains blocked in this runtime by missing dependencies, starting with PyJWT. The pinned Next.js 16.3.4 package was unavailable offline. PostgreSQL startup was checked through the adapter against a simulated connection. Live PostgreSQL, Gemini, and deployment still need verification in a configured environment.
